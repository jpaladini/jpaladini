> This one's about the machines talking to each other rather than the machines doing the work. We spent this morning getting two separate OpenClaw instances — one on a MacBook Pro, one on an always-on Windows/WSL2 box — to actually coordinate instead of just each doing their own thing in isolation. Here's what that took.

## TL;DR

- **The goal:** a Mac OpenClaw (personal context, iMessage, desktop/browser control) and a Windows/WSL2 OpenClaw (always-on, GPU, cron jobs, central data) needed a way to work as a pair instead of two unrelated assistants.
- **First blocker was boring but total:** the PC's CLI wouldn't start. A newer config key had leaked into its config from a version the PC wasn't actually running yet, and the older binary just refused to boot with it present.
- **We weighed three ways to link them** — a reverse SSH tunnel, bridging through iMessage, and a shared Discord server with two separate bots — and picked the one that didn't quietly merge two identities into one.
- **Along the way:** a secrets-handling scare that turned out to be a mix-up rather than a leak, and a Discord bot setup that threw an unhelpful error before it threw a helpful one.

---

## Why bother linking them at all

The two instances aren't redundant, they're complementary. The Mac has my iMessages, my desktop state, my browser — the stuff that's inherently personal and local. The WSL2 box is the one that's on 24/7, has the GPU, hosts the cron jobs, and sits closest to the central data store. Up to today, they'd never talked to each other; any coordination ran through me, manually, relaying context back and forth. The obvious next step was giving them a channel to coordinate directly, with me still approving anything that leaves the building.

## The CLI wouldn't start

Before any of that, the PC side needed to be reachable at all, and it wasn't. SSHing in from the Mac side was fine — the box was up, the shell was fine — but the OpenClaw CLI itself refused to start.

The cause was a single config key: `compaction.enabled`. It had ended up in the PC's config file, but the PC was still running an older release (think `2026.6.11`) than the one that key belongs to (`2026.11.3`-class). The older CLI didn't recognize the key, and rather than ignoring it silently, it refused to boot — which, annoying as it was in the moment, is the behavior you want from something that's supposed to be always-on. A config it doesn't understand is exactly the kind of thing that should fail loud, not fail weird three days later.

The fix was unglamorous: back up the config file, remove the one offending key, restart, and verify the CLI came up clean before touching anything else.

```jsonc
// before — blocks startup on the older release
{
  "compaction": {
    "enabled": true
  }
}

// after — key removed, startup succeeds
{
  // (compaction block removed entirely)
}
```

Lesson filed away: don't let a config file get ahead of the binary that reads it. If a feature key shows up in a config, the release that understands it needs to land first, or get pinned together.

## Three ways to link two agents, and why we didn't pick two of them

With the PC reachable again, the actual design question was: how should two independent OpenClaw instances coordinate?

**Option 1: reverse SSH tunnel, with the Mac pointing at the PC's gateway.** This is the most direct path, and also the wrong shape for what we wanted. Pointing one gateway's `gateway.remote` config at the other doesn't link two independent agents — it makes one gateway *become* a front end for the other. That's fine if you want one brain with two bodies. It's not fine if you want two agents that can disagree, specialize, and check each other's claims, which was the actual point of this exercise.

**Option 2: bridge through iMessage**, with the PC reaching the Mac's Messages app over an SSH wrapper so both agents could "speak" into the same thread. Rejected for an identity reason, not a technical one: two bots replying from one Apple ID aren't two participants in a conversation, they're one identity talking to itself with extra steps. Anyone reading the thread — including me — would have no way to tell which agent said what without digging into metadata that the interface itself doesn't surface.

**Option 3: a shared Discord server, with two separate bot accounts.** This is what we went with. Two distinct bot identities, in the same channel, each clearly labeled, each able to @-mention the other, each with its own token and its own permission boundary. It's the only one of the three options where the two agents are visibly, individually accountable for what they say — which mattered more than the extra setup overhead.

## The secrets scare that wasn't

Getting there needed real credentials — a 1Password vault with a scoped service account for one side, a Discord bot token for the other — and credentials are where I wanted the most friction, not the least.

The rule we set going in: a token is referenced, never pasted. Config files hold a `SecretRef` that points at a vault item; the actual value gets resolved locally at runtime and never touches chat, logs, or a committed config.

```yaml
# config.yaml — a reference, not a value
secrets:
  discordToken:
    ref: "op://<vault-name>/<item-name>/token"
```

That discipline caught something real almost immediately: a 1Password trust check flagged a group-writable directory in the local Homebrew install path on the Mac side. Anything with write access to that directory could, in principle, have tampered with a binary 1Password's CLI trusted. The fix was straightforward — tighten the directory back to non-group-writable — but it's exactly the kind of gap that's easy to miss on a machine that's been configured gradually over a long time rather than built fresh.

The other near-miss was dumber and more human: at one point we briefly confused the rotated 1Password service-account token with the Discord bot token — two different secrets, two different purposes, living in two different vault items — and started debugging the wrong one against the wrong symptom. Unwinding that cost a few minutes and taught a one-line lesson: name secrets for what they unlock, not for which setup step you were on when you created them.

No secret value appeared in this channel, in a commit, or in a config file at rest, at any point. That was the one rule that mattered most and the one we didn't bend.

## Getting Discord actually working

The Discord side had its own small, specific potholes.

The setup wizard's first failure mode was a flat, unhelpful `token must be a string` — which is technically true and practically useless as an error message when you're staring at a token that very much looks like a string. The real cause turned out to be a duplicate plugin installation shadowing the one actually being configured. `doctor --fix` resolved it, but only after the gateway process itself was stopped — running the fix against a live gateway just meant it kept re-creating the thing it was trying to clean up.

The bot invite itself needed explicit **Server** access scoped on the OAuth invite, not just bot permissions within a server it was already in — an easy thing to get backwards once you're three tabs into Discord's developer portal.

And because two bots now share a channel, we added guardrails before letting them talk: mention-only responses (no answering every message in the channel by default), bot-loop protection (so the two agents can't accidentally ping-pong each other into a runaway exchange), and a guild/channel allowlist so neither bot is listening anywhere it hasn't been explicitly invited.

```yaml
discord:
  token:
    ref: "op://<vault-name>/<item-name>/token"
  mentionOnly: true
  loopProtection: true
  allowlist:
    guilds: ["<guild-id>"]
    channels: ["<channel-id>"]
```

## The first actual conversation

Once both bots were live in the same channel, the first real exchange was the coordination meta-conversation itself: what should each side own, and what rules keep this safe.

The split that came out of it: the WSL2 box owns always-on work, cron-scheduled jobs, and anything touching the central data store, since it's the one that's never off. The Mac owns personal context and anything that's inherently Mac-only — iMessage, desktop state, local browser sessions. Three ground rules came with it: no secrets ever get pasted into the shared channel, anything that sends a message, spends money, or changes config on my behalf needs my sign-off first, and every task gets a single named owner with handoffs shaped like `TASK / NEEDS / DONE-WHEN` so nothing gets silently dropped between two agents each assuming the other has it.

## The honest part

Partway through that first conversation, I asked the WSL2 agent what cron jobs it currently had running. It told me none. That was wrong — a daily research digest had actually been posting to this Discord server for months, and had run again just the day before.

The correction, once I pushed back, was straightforward: it had checked one scheduling mechanism, gotten an empty result, and reported that as "nothing is scheduled" rather than "nothing is scheduled *in the place I checked*." The job existed in a different project directory than the one it first looked in.

Nothing here is a disaster — just a reminder worth writing down. An agent's claim about its own state is a hypothesis, not a fact, until it's actually been checked against the filesystem, the logs, or (in this case) the channel where the evidence was sitting the whole time. "I didn't find it" and "it doesn't exist" are different claims, and the gap between them is exactly where this kind of mistake lives. We're keeping that one as a standing rule for both agents going forward: verify, don't just report an empty search as an empty truth.
