> Daily devlog, compiled from what actually happened in the repos rather than from memory. Today was a single-repo day: I spent it wrestling the Gmail API into submission for an inbox-cleanup tool, and the lesson was less "add more retries" and more "stop lying to yourself about how fast the API really is."

---

## TL;DR

- **The inbox-cleanup pipeline was drawing sustained 429s.** Fetching message metadata in batches of 100 bursts 500 quota units at once; Gmail throttled it into the ground and the run died once retries ran out.
- **The real fix was a queue with per-item requeue.** Instead of re-executing an entire failed batch, rate-limited sub-requests now go back on the queue individually with a growing backoff — so throttling degrades throughput instead of killing the run.
- **Then I measured the limiter and it was slower than documented.** The per-user limit is nominally ~250 quota units/sec, but in practice it admitted closer to 100–125. Batches of 40 still got ~half their sub-requests 429'd every time, so metadata batches came down to 20 — and I stopped escalating backoff on *partial* rejections, which was quietly collapsing throughput.
- **Classification rules got hardened.** Category-based catch-alls, more notification senders, and a protect-list for accounts I never want auto-swept (insurance, shipping, `.gov`).

---

## The setup

The [`comms`](https://github.com/jpaladini/comms) repo holds a small Gmail cleanup pipeline — survey, classify, apply, report, restore — driven by a `rules.yaml`. The idea is boring on purpose: crawl the inbox, pull just enough metadata (`From`, `Subject`, `Date`, `List-Unsubscribe`) to classify each message, then apply labels/archival according to declarative rules, with a report and an undo path so nothing is irreversible.

The classify step needs metadata for *every* message it's considering, and that's where the whole thing kept falling over.

## The 100-batch trap

Gmail's `messages.get` supports HTTP batching, and the API rejects batches over 100 sub-requests — so of course the first version used 100. That's the trap. A `messages.get` in `metadata` format costs **5 quota units**, so a batch of 100 fires **500 units in a single burst**. Gmail's per-user budget is roughly 250 units/second, so every batch immediately overran the budget, drew a wall of `429 rateLimitExceeded`, and leaned entirely on retry backoff to claw its way through. On a large inbox that meant retries eventually exhausted and the run just stopped.

The original retry logic also made things worse in a subtle way: when *some* sub-requests in a batch came back rate-limited, it would raise and re-run the **whole** batch through the outer backoff — re-bursting the requests that had already succeeded right alongside the ones that hadn't. Throttling begets more throttling.

## Fix #1: a queue, not a loop

The first real fix rewrote `fetch_metadata` from a "for each chunk, execute, maybe retry the chunk" loop into a **work queue**:

- Pull `BATCH_GET_SIZE` ids off the front of the queue.
- Execute the batch. Successful rows get committed incrementally (so the run stays resumable).
- Sub-requests that come back with a retryable status get **re-queued individually** — put back on the front of the queue — never re-bursted as part of the original chunk.
- Hard failures (non-retryable) are logged and skipped rather than killing the batch.

Batch size dropped from 100 to 40 with an added `BATCH_PACE_SECONDS` gap between batches. This is the shape you want: the failure mode is *slower*, not *dead*.

## Fix #2: believe the limiter, not the docs

With per-item requeue in place I could actually watch what the limiter was doing — and it wasn't doing what the docs promised. Even at batches of 40 (200 units/burst, comfortably under the nominal 250/sec), **roughly half of every batch's sub-requests came back 429'd**. The practical admission rate looked more like **100–125 units/sec**, not 250.

Two changes fell out of that observation:

1. **Batch size down to 20.** Twenty gets is ~100 units — right at the edge of what the limiter actually tolerates — with a shorter fixed pace between batches.
2. **Stop escalating on partial rejections.** The backoff was escalating (`2^streak`, capped at 60s) on *any* rate-limiting. But partial rejections are the *normal, healthy* state when you're running near the limit — escalating there just crushed throughput for no reason. Now the escalating backoff only kicks in when an **entire** batch is rejected (a sign something is genuinely throttling hard); a partial rejection takes a brief fixed pause, requeues the stragglers, and **resets** the streak.

The mental model that made it click: near a rate limit, a steady trickle of 429s isn't an error condition to back away from — it's the limiter doing its job while you make progress. The trick is telling "we're saturated and fine" apart from "we're locked out," and only panicking about the second one.

An opinionated aside: the documented quota number was actively misleading here. If I'd trusted "250 units/sec" and tuned to it, I'd have shipped something that 429s half the time and blamed my own code. Measuring the real admission rate was worth more than any amount of reading the quota page.

## While I was in there: rule hardening

The other commit of the day was to `rules.yaml`, mostly making the classifier both safer and more aggressive at the same time:

- **A protect-list for things I never want auto-swept:** insurance and shipping senders (Progressive, UPS) joined the existing `.gov` and account-security protections. Protected rules always win over the catch-alls.
- **More notification senders** routed straight to their bucket: LinkedIn message/digest addresses, USPS Informed Delivery, Google Alerts, Google Voice.
- **Category-based catch-alls.** Anything Gmail itself already filed under **Promotions** is treated as marketing — with or without a `List-Unsubscribe` header, since a lot of older marketing mail predates that header. And bulk mail (List-Unsubscribe present) in the **updates / social / forums** categories is marketing too. Deliberately **not** applied to `personal` — the whole point is that a human's actual correspondence never gets swept up in a catch-all, no matter what headers it carries.

Plus the least glamorous commit of the day: adding run logs to `.gitignore` so the cleanup runs stop trying to commit their own output.

## What's next

The rate-limiter work is the kind of thing you only trust after a full run against a real inbox, so the next step is exactly that — a long survey pass end-to-end to confirm the 20-batch pacing holds steady without exhausting retries, and to see whether the new catch-all rules classify the long tail sensibly or need another round of protect-list tuning. The nice property of the pipeline is that it has a restore step, so I can be aggressive with the rules and walk back anything that gets miscategorized.
